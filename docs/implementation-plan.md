# Clavis: Implementation Plan

Status: v0.1
Inputs: `docs/specs/piano-learning-model-spec.md` (v0.3), `docs/specs/piano-trainer-architecture.md` (v0.1)

Scope of this document:

- Section 1 resolves gaps and contradictions in the specs that would otherwise block implementation.
- Sections 2-4 break M0-M2 (the critical path to daily ear training on iPhone) into PR-sized tasks with acceptance criteria.
- Section 5 outlines M3-M7 as epics; each gets a task-level plan when it starts.

Working assumptions:

- Implementation is mostly done by Claude, one PR per task (roughly 200-800 changed lines), each with tests that prove its acceptance criteria.
- Router: SvelteKit with `adapter-static` (SPA fallback, `ssr = false`). Closes arch open question 1.
- The repo is the monorepo root (no `piano-trainer/` wrapper directory).

## 1. Spec resolutions

These are proposed decisions. Each is cheap to change now and expensive after M2, because they shape event schemas and item identity.

| # | Issue in specs | Proposed resolution |
|---|---|---|
| R1 | Spec 5.1 says "degrees: one item per degree per key family", but 3.4 says EAR is key-independent with a randomised tonic | EAR item identity excludes key: `itemId = hash(nodeId, {mode, degree})`. Tonic is a **presentation** parameter chosen at runtime. Same for progressions and cells |
| R2 | Refold must be deterministic, but generators use randomness (tonic, register, cell content) | `item.presented` carries the full presentation params (tonic, register, notes, seed). Reducers never call generators; replay never needs to regenerate a stimulus |
| R3 | Away-mode rating cap is keyed by input source, but "singing without piano" uses the mic, same as singing at the piano | Add `mode: "instrument" \| "away"` to `session.started`. The rating cap and mastery-window filter use session mode, not `inputSource`. `inputSource` stays for scoring tolerances. Add `"tap"` to `NoteEvent.source` |
| R4 | `node.transitioned` is stored as an event, but node state is also derived by the fold. After a cross-device refold, stored transitions can contradict derived state | Node states are **derived only**. Replace `node.transitioned` with `node.introduced` (the composer's `available -> learning` decision, which is a real choice, not a derivation). Transitions for milestones/UI are computed by diffing folds |
| R5 | Placement results must seed node states, but there is no event for it | Add `placement.completed { results: Record<nodeId, "mastered" \| "fluent" \| "available"> }`. Reducer treats it as an override floor that ongoing demotion can lower |
| R6 | "distinctSessions with >= 1 day between" and "new items per day" need a day boundary | `session.started` records `tzOffsetMin`. "Day" = learner-local calendar date of the session start. Day rollover at 04:00 local (so late-night practice counts as the same day) |
| R7 | Events carry `userId`, which breaks "anonymous local use, then claim on sign-up" | Client events do not carry `userId`. The server binds events to the user from the auth token at push time. Claiming = first authenticated push. Envelope: `{ id: ULID, deviceId, at, v: schemaVersion, ...payload }` |
| R8 | Snapshots go stale when reducer logic or content changes | Snapshots keyed by `(reducerVersion, contentVersion)`. Mismatch = discard and refold from zero. Event volume makes this cheap |
| R9 | Placement step 3 (LH I-IV-V-I, melody + block chords) needs polyphonic input, which arrives in M5 | Placement ships in M3 with EAR and READ sections only. HANDS section added in M5; until then `hands.*` roots are `available` |
| R10 | `read.minor.accidentals` and `hands.minor.leadingTone` are referenced in 3.4 but absent from the graph tables | Add both. Proposed prereqs: `read.minor.accidentals` <- `read.bass.skips`, `ear.degrees.minor`; `hands.minor.leadingTone` <- `hands.lh.triads.root`, `ear.degrees.minor` |
| R11 | Key-family unlocking rule (for key of the day and per-family mastery) is undefined | A node's family B items become eligible once that node is `mastered` in family A; family C once `fluent` in B. Key of the day rotates around the circle of fifths over keys whose family is unlocked for at least one `learning` node |
| R12 | "Sing, then play" generators (`degreeSing`, `cellEcho`) have two responses but one `AttemptOutcome` | **Superseded by R29:** singing is no longer graded; attempts have a played part only. Sung sub-scores stay readable in old events. One attempt with sub-scores `{ sing?, play? }`. **Amended in T2.14:** at the instrument the attempt is correct only when both parts are (spec 7: "sung pitch within 50 cents; key correct"), latency comes from the played part, and `partial` is the mean of the sub-scores when either part has partial credit. Away mode rates the single part it has. Errors are tagged with their part (`detail.part`) so feedback can say "you sang" or "you played" |
| R13 | Estimated seconds per item (composer budget) has no data source at first | Derived from `item.presented -> attempt.completed` durations, rolling median per generator. Seed with constants per generator in content |
| R13a | Event versions after the first shipped schemas | **Added in T2.15:** `session.started` and `settings.changed` have v2 (v2 adds optional `practice` and optional `newItemsPerDay`). Both registry entries accept v1 and v2; the upcaster lifts v1 to v2 by setting `v: 2`. New events are written as v2. REDUCER_VERSION is 2 |
| R14 | Spec 3.2 gives a node a single `itemGenerator`, but degree nodes are drilled by both `degreeSing` (sing then play) and `degreeId` (play only, and the Away tap variant) | `SkillNode.itemGenerators: GeneratorId[]`, non-empty, first entry is the default. Item identity (R1) excludes the generator, so all generators for a node share one FSRS card per item |
| R15 | Spec 5.1 says "one item per note per clef position" and spec 3.4 tracks READ mastery per key family, but R1 leaves the key out of item identity and the composer ignores family, so a node mastered in family A never gets B or C items | For key-dependent nodes the item params include the family: `itemId = nodeId\|fam=A\|pos=F3` (`pos` is the staff position, not the sounding pitch). The key is chosen at presentation: the key of the day if it is in the item's family (in the node's mode), else a seeded pick from `keysInFamilies([fam])`, recorded in `presentation.key` (R2). A family is open for a node when: A, the node is `learning` or beyond; B, `byFamily.A` is `mastered`; C, `byFamily.B` is at least `fluent` (R11). New items come from every open family of any key-dependent node at `learning` or beyond, key-of-the-day family first, then A, B, C. **C major first:** until `read.bass.landmarks` is `fluent`, READ items use C major only (A minor for minor items); after that, all of family A. EAR is unchanged (R1) |
| R16 | Spec 13 allows one new concept per session, but the composer only introduces EAR nodes, the EAR fill uses up the new-item cap, and Away sessions are EAR only although spec 6.5 makes READ recognition Away-eligible | Each strand may introduce a node when none of its own enabled nodes is `learning`; still at most one introduction per session. If both strands have a candidate, the strand whose last introduction is older wins (ties: EAR). READ introductions emit `node.introduced` with `keyFamily: "A"`. When READ has new candidates it reserves `floor(allowance / 2)` new items. Away: no Orient; Ear 60% and Read 40% when Read has Away-eligible content, else all Ear |
| R17 | Latency is "stimulus end to first correct response", but reading items have a visual stimulus with no audio end | Reading items play no audio preview. The reference time is when the notation is painted (converted to the AudioContext clock); for `rhythmRead` it is the end of the count-in, which starts after the notation is shown. The reference audio plays only in feedback, as replay (spec 8.5) |
| R18 | Enabling `bassNoteRead` enables five nodes, including intervals and minor accidentals; `bassChordRead` and `sightLine` need polyphonic input and DTW (M5) | In M3 `bassNoteRead` covers landmarks, steps, skips, minor accidentals and an interval variant (two notes, the first on a landmark, the second a 2nd to 5th away, scored as an exact-octave `sequence`). `rhythmRead` ships. Deferred to M5: `bassChordRead`, `sightLine` (grand staff nodes) and the Read block's closing line |
| R19 | Spec 4 says placement results "seed node states" without thresholds | Placement writes only `placement.completed` (no session, item or attempt events). Instrument mode only. EAR: 9 `degreeId` items in C major (1, 3, 5, three each); 8+ correct with median latency within target is `mastered`, 7 is `fluent`, else `available` and the section stops; if 1-3-5 is mastered, 8 diatonic items (2, 4, 6, 7 twice) follow with the same rule (n-1 correct with median latency within target is `mastered`, n-2 is `fluent`: 7 and 6 of 8). READ: 10 `bassNoteRead` items in C major (4 landmarks, 3 steps, 3 skips); all correct within target is `mastered`, 3 of 4 or 2 of 3 is `fluent`, else `available`. Never above a prerequisite; the section stops at the first `available`; results only raise nodes (R5). Placement writes no cards, so the composer treats uncarded items of a node at `fluent` as new items (under the daily cap); in EAR they alternate with learning nodes' new items, learning first. Uncarded items of `mastered` nodes are offered only when the strand has nothing else to introduce |
| R20 | Phone mics often detect C2-B2 piano notes an octave high, and exact-octave bass reading depends on it | If real bass-register fixtures show mic octave accuracy below 95%, mic answers to exact-octave items are graded by pitch class with `detail.octaveUnverified` and can raise a node to `fluent` but never `mastered`. MIDI and the on-screen keyboard stay octave-exact |
| R21 | Spec 7 lists `chordQuality` as "choose major/minor/dim, or play it" and says on-screen responses are used in Away mode only, but a chord's quality is not a pitch the learner can play or sing before M5 (polyphonic input), so there is nothing to play | Add an expected-response kind `choice` (`options` with ids and labels, and the id of the `correct` one) answered with on-screen buttons in both modes. Buttons are allowed at the instrument for answers that are not a pitch. Scoring is `scoreChoice`: the right button is correct with latency from the end of the stimulus, another button is `choice.wrong` naming both options, no pick in the response window is `response.timeout`. Mastery credit follows the session mode as in R3 (a choice answered at the instrument counts toward mastery; in Away mode it is capped like any Away attempt). Guessing is handled by the mastery window (90% over 20 attempts). Source is recorded as `tap`. Diminished triads join `qualities` in a later graph version |
| R22 | Piece phrases (MP, TP.4) need a place in the model: attempts must hit a graph node, a phrase is graded on pitch and rhythm together, and no spec says what a finished piece is | **Node.** One graph node `apply.pieces` (new strand `APPLY`, generator `pieceLine`) holds every phrase item, `apply.pieces|phrase=N|piece=<id>`. Its mastery state is not used: unlocking is per piece (`listPieces`, every required node at least `fluent`) and progress is `state.pieces`, derived from phrase attempts and `piece.completed`. **Grading.** A new `line` play target (exact pitches and onsets) is scored in two stages, pitch first with `sequence` rules, then rhythm with `rhythm` rules only once the pitches are right. Correct needs both; `partial` is 0.7 pitch plus 0.3 rhythm. **Composer.** `blocks.apply` is `null` or the phrases for the session: due phrases first, then up to 2 new phrases of the current piece (the first unlocked piece not yet played through). It is never planned in Away mode or practice. Apply takes about a third of the daily new-item allowance (rounded) so reading cannot use it all. **Runs.** `composePieceRun` plans every phrase of a piece in order (`plan.run`). The session writes `piece.completed { pieceId, phrases, correctPhrases }` once all phrases were attempted; the piece counts as played through when `correctPhrases === phrases`. **Rollout.** `pieceLine` stays `implemented: false` and is not in the app registry until the enabling PR (TP.5), so nothing changes for learners yet |
| R23 | Playing a learned tune by ear (MP, TP.6) needs a node, a rule for when it is offered, and a way to show the score only after the answer | **Stages superseded by R29:** hear, cue (ungraded), play, reveal; there is no `sungSequence`. **Node.** A second APPLY node, `apply.piece-ear`, with the `pieceEar` generator (injected like `pieceLine`). Its items are `apply.piece-ear\|phrase=N\|piece=<id>`, so they never share a card or a phrase record with reading: only `pieceLine` attempts feed `LearnerState.pieces`. **Offered** for a piece once every phrase of it has been played correctly at least once (the same "learned" the Home card shows), one new phrase per session (`APPLY_NEW_EAR_PHRASES_PER_SESSION`), ahead of new reading phrases, in the instrument only. **Stages.** The item plays a one bar count-in and the phrase at 60 bpm with its real rhythm; the expected response is a `sungSequence` and then the same `line` as reading (R12: both parts must be right, errors tagged `sing` or `play`). Rhythm is fitted to the learner's own pace, so playing needs no reference beat. **Reveal.** `ItemInstance.reveal` is the phrase as a score. The machine draws it with the feedback (not before), marks the notes, and holds the feedback until the learner moves on. Feedback names sung notes as sung ("you sang E4"). |
| R24 | Sessions and practice grew features outside any plan task: choosing skills, the on-screen keys as an answer, a free keyboard page, the daily warm-up, where rhythm and targets sound | **Practice.** `/practice` lists started skills with answered items; `?practice=1&skills=a,b` drills only those (`ComposeInput.skills`). A practice round always offers the try-first step (Ready) for degree items. **Input.** At the piano the mic or MIDI and the on-screen keys answer together (`CompositeInputAdapter`); an answer made only on the keys is graded and logged as `tap`. `/keyboard` is a free-play page (key picker, home note and chord marked, hear the key): nothing is graded or stored. **Warm-up.** The key-of-the-day orient block is planned only before the first finished, non-practice session of the day that presented an item; otherwise its share goes to ear. **Rhythm.** `rhythmEcho` sounds on the tonic of the key of the day. **Register.** Degree targets (and melodic cells, when they fit) sound in the register of the cadence's last chord, so 1, 3, 5 and the other degrees are heard in one place; another keyboard range falls back to its centre. **Introductions.** Pitch skills are introduced before rhythm nodes. |
| R26 | Left-hand chords (T5.3, `lhPattern`) need a polyphonic input, a response kind for several notes at once, and a rule for who is offered them | **Input.** `ComposeInput.polyphonic` is true only when the session's input is MIDI; a generator listing `polyphonic` in `requires` is dropped from the plan, and its node is not introduced, without it. Mic, tap and Away never get HANDS items (the generator is also not Away eligible). Home's own previews do not know the input, so they ignore HANDS. **Item.** `hands.lh.triads.root` only; an item is a progression of four root-position triads from I, IV, V and vi that starts on I and never repeats a chord twice running (the `bassMotion` universe), per key family (R15): `hands.lh.triads.root|fam=A|prog=I-IV-V-I`. The key is presentation. Chords are half notes over two bars at 60 bpm after a one-bar count-in, on the bass staff in C2 to C4, each root nearest the previous one; chord numerals and symbols are text beside the staff. **Response.** A new expected kind `chordLine` (each chord's tones, numeral, symbol and onset), scored by `scoreChordLine` over `alignPerformance`. Correct only when every chord tone has the right pitch (nothing wrong or missed), at most one stray extra note, and the overall alignment score is at least 0.8; `partial` is that score. Errors `chord.wrong-tone`, `chord.missed`, `chord.missing-tone`, `chord.extra`, `chord.early`, `chord.late` name the chord, so feedback reads "You played E instead of F in the IV chord". The phase ends when every tone is struck and the hand has been still for 0.8 s, or after 5 s of silence with tones missing, or at the response window. **Composer.** HANDS items share the Apply block with pieces: due ones first, then up to two new ones, ahead of new piece phrases, under the same new-item cap and with HANDS as a third strand in introductions (oldest introduction first, ties EAR, READ, HANDS). Not in practice rounds. Cards are ordinary FSRS cards; spec 5.4 task-level priority and micro-drill spawning are not built. **Graph.** The other nodes that listed `lhPattern` (`hands.lh.inversions`, `hands.lh.broken`, `hands.lh.pop`, `hands.minor.leadingTone`) moved to the new unimplemented `lhPatternVariants`, so they stay disabled. |
| R27 | M5 was to be planned after S1, but S1 is blocked on the two-hand recordings (T1.8), while the rest of HANDS only needs polyphonic input that MIDI already gives (R26) | **MIDI first.** Every M5 task below ships for MIDI input only (`requires: polyphonic`, R26). Mic transcription (T5.12) waits for S1; when it lands, `ComposeInput.polyphonic` widens to mic and nothing else changes. **Grand staff.** `ScoreSpec.staves` allows 1 or 2; two staves are treble then bass with a brace, the same meter and measure count. Note ids stay unique across the score. `expectedFromScore` reads every staff and tags each note with its `hand` (`rh` for treble, `lh` for bass). **Response.** A new expected kind `performance` (notes with id, MIDI, onset and duration in beats, hand; tempo; beats per bar), scored by `scorePerformance` over `alignPerformance`: correct when no note is wrong or missed, at most one stray extra and overall at least 0.8, `partial` is overall (the R26 rule). Errors `note.wrong`, `note.missed`, `note.extra`, `note.early`, `note.late` carry measure, beat and hand, so feedback reads "bar 3: LH late". Monophonic HANDS patterns (broken, Alberti, pop) use the existing `line` kind. **Task priority (spec 5.4).** A task is a HANDS or BYEAR node. `LearnerState.tasks[nodeId]` holds `lastPracticedAt` and a rolling score (EWMA, alpha 0.3, of `partial`, or 1 and 0 for correct and wrong). Apply picks one task, the one with the highest `daysSince x (1 - rolling)`, and fills from that node's due items, then its new items; pieces keep their R22 share. **Micro-drills.** A failed `chordLine` or `performance` attempt spawns at most one drill item for the first erring chord change, an item of the same node with params `drill=<from>-<to>` (the two chords played twice), logged as `drill.spawned` v1 `{ sessionId, sourceItemId, nodeId, itemIds }`. Drill items are never listed as new; their card is due at once and is an ordinary FSRS card after that, at most 3 per node. Due drills go first in Apply. **Task and drill details (T5.8).** Only tasks with something to offer (due items, or new ones while the allowance lasts) compete, and a node being introduced is the task. `daysSince` is fractional; a learning task never practised ranks first (infinite priority), a node at `fluent` or beyond with no attempts (placed) counts as practised now with a perfect score; ties go to the task practised longest ago, then graph order. Drill attempts leave the rolling score alone. The first erring chord is the lowest chord index any positioned error names (`chord.*` index, or the bar and beat of a `note.*` error); the drill is the change into it, or out of it for the first chord; a drill never spawns a drill, and practice spawns none. At the cap a new drill retires the oldest (its card is removed); spawning a live drill again makes it due now. Due drills of every task node go first, whichever task is chosen. **Placement (spec 4 step 3).** A HANDS section runs only with MIDI input: one `lhPattern` item (I-IV-V-I in C), then one `coordTask` item. A correct item places its node at `fluent`, otherwise `available`; without MIDI the section is skipped and R9 holds |
| R28 | T6.5 bundles two unrelated features, and its plan row leaves open the benchmark content, how a recording maps to a month, the replay UI and the calibration formula. Arch open question 2 (attempt replay retention) is still open | **Split.** T6.5 is the benchmark; T6.6 is self-assessment. **Benchmark options (spec 14, decision 9).** Library pieces only (not imports): the up to four unlocked pieces with the highest `difficulty`, padded with the lowest-difficulty library pieces when fewer than three are unlocked. **Recording.** The learner plays the whole piece from its score, not graded. Audio via `MediaRecorder` (Opus WebM, or MP4 on Safari), at most 3 minutes, stored with the T4.5 `BlobStore` as `benchmark-<ulid>.<ext>`, `pinned: true`, and uploaded by the existing queue. **Month.** `benchmark.recorded` v1 `{ benchmarkId, pieceId, month: "YYYY-MM", blobKey, contentType, durationMs, sizeBytes }`, with the month in the learner's local time zone at recording. One benchmark per month: recording again in the same month replaces it (the reducer keeps the latest per month; the app deletes the superseded blob locally and, when signed in, in R2). The event syncs, so another device can list benchmarks and fetch audio with a new `GET /api/blobs/:name` client helper, cached locally and pinned. **Prompt.** Home and `/progress` show "Record this month's benchmark" while the current month has none. **Replay.** `/progress/benchmarks`: benchmarks grouped by piece, newest first. Choosing a piece shows its score once and two players side by side, this month and an earlier month (default the oldest), plus "Play one after the other". **Self-assessment (spec 8.4).** Asked only for nodes at `fluent` or `mastered`, on every third such attempt in a session (attempt index mod 3 is 0), never in placement, practice, piece runs or revealed items, nor when no answer was given. After the answer and before feedback the learner taps "I got it right" or "I got it wrong"; feedback then shows as usual. Logged on `attempt.completed` v2, which adds optional `selfAssessment: "right" \| "wrong"` (upcast by `liftToV2`). It never changes the rating. **Calibration (spec 12).** Over self-assessed attempts in the last 28 days: agreement is the share where the self-assessment matches `outcome.correct`, plus overconfident (said right, was wrong) and underconfident counts. Shown on `/progress` with a 12-week weekly agreement trend once there are at least 10 self-assessed attempts. **Retention (arch open question 2).** Only benchmarks are kept as audio and only they go to R2. Raw `NoteEvent[]` per attempt is not persisted; replay stays in-session. Closes plan open item 4 |
| R25 | The by-ear capstone loop (spec 9, T7.2) has seven stages and several nodes, but only the melody stage can be graded today, `byEarPhrase` was listed by three nodes, and BYEAR is not a block in spec 6.2 | **Stages superseded by R29:** hear, cue (ungraded), play, reveal; the register follows the keyboard range. **Stages.** `byear.melody.simple` runs hear (after the key-setting cadence), sing (`sungSequence`), play (a `line`: exact pitches, then rhythm fitted to the learner's pace) and reveal (the score drawn after the answer, as in R23). Both parts must be right and errors name their part (R12). Left out: "find the tonic" (the cadence sets home), bass and harmonise (polyphonic input, `byear.harmonise`), and the cross-session gating of later stages (nothing later exists yet). **Items.** `byear.melody.simple\|bars=N\|slot=K`: 3 lengths (4, 6, 8 bars of 4/4) x 6 slots = 18 melodies, each a pure function of its id (seeded rejection sampling: diatonic, mostly stepwise, starts on 1, 3 or 5, half close on 2, 3 or 5, ends on 1, within an octave). The key is a presentation parameter in a major key (R1) and the register follows the learner's voice range; the presentation carries the degrees, beats and MIDI notes (R2). **Generators.** `byEarPhrase` is the melody stage only. `byear.harmonise` moves to `byEarHarmonise` and `ear.real.phrase` and `byear.full.phrase` to `byEarRecording` (both unimplemented), so they stay disabled and no synthetic content ships as "real recordings". **Composer.** BYEAR melodies go in the Apply block (spec 6.2: "one HANDS or BYEAR task"), instrument mode only: a BYEAR node is introduced like any node (strands take turns, oldest introduction first, ties to EAR, READ, BYEAR), then one new melody per session plus due ones. Spec 5.4 task priority and error micro-drills are not built; FSRS cards schedule the melodies like other items. `contentVersion` 2026.10.11 |
| R29 | Clavis is about learning to play by ear, not about testing the learner's singing, so grading the voice (R12) works against the point and fails learners for pitch-tracking and vocal-range reasons that have nothing to do with piano | **Graded singing is removed; singing is an ungraded cue.** After the learner hears the target the app prompts "Sing or hum it, out loud or in your head" (`ItemInstance.cue`), with Hear it again and Ready. No mic listens to the voice and the cue has no timer; the answer window and latency start at Ready. Only the played answer is graded. **R12** is superseded: attempts have a played part only (`subScores` is `{ play }`; old events with `sing` sub-scores and `voiceRangeLow/High` settings still parse and refold unchanged). **R23** (`apply.piece-ear`): the stages become hear, cue, play, reveal; the `sungSequence` expectation is gone. **R25** (`byear.melody.simple`): the same stage change, and the register follows the keyboard range (`DEFAULT_KEYBOARD_RANGE`), not a voice range. **Away mode:** degree items are answered on the on-screen keys (the `play` target, logged as `tap`; `degreeSing` is a historical id that behaves like `degreeId`). The R3 Away mastery cap is unchanged. **Compatibility:** generator ids, node ids and item ids are unchanged (FSRS cards and history are keyed on them). `expected.sing` stays in the schema so older data parses, but no generator emits it and scoring ignores it. The voice range setting, the Settings control and `GenerateContext.voiceRange` are removed. `pieceEar` and `byEarPhrase` no longer require `mic`. `contentVersion` 2026.10.13 |

## 2. Cross-cutting decisions

| Area | Decision | Why |
|---|---|---|
| Package manager / runtime | pnpm workspaces, Node 22 LTS, TS `strict`, ESM only | Matches arch; one toolchain for web, worker and Node-side tests |
| Boundaries | `dependency-cruiser` rules in CI: `core` imports no workspace package; `scoring` imports only `core` types; `audio`/`notation` never import `core` logic | Enforces arch section 3 mechanically, so agent PRs can't erode it |
| Theory helpers | `core/theory` wraps `tonal` (keys, degrees, voicings, register clamping) | Generators and composer both need it; external libs are allowed in `core` |
| Determinism | All randomness via an injected seeded RNG (`pure-rand` or a tiny xoshiro); all "now" via injected clock | Golden tests for composer, reproducible refolds |
| Audio threading | `postMessage` with transferable buffers, **not** `SharedArrayBuffer` | SAB needs COOP/COEP cross-origin isolation, which complicates sample/WASM loading and iOS. Revisit only if profiling demands it |
| Samples | Self-host the `smplr` piano samples (subset of velocity layers, one or two mic positions) as static assets, precached | `smplr` defaults to a remote CDN, which breaks offline use |
| Persistence API | `EventStore` interface in `core/events`; Dexie implementation in `apps/web`; in-memory implementation for tests | Keeps `core` DOM-free while reducers and composer are tested against the real interface |
| Repo conventions | Root `CLAUDE.md`: commands, boundaries, test expectations, event-schema change rules (never edit a shipped schema version; add a new one with an upcaster) | Each PR is implemented by a fresh session; conventions need to live in the repo |
| Licences | Record in `docs/licences.md`. Note Verovio is LGPL-3.0 (fine as a separately loaded WASM module; keep it unmodified or publish changes) | Product-later constraint |

## 3. Milestone dependency overview

```
M0 skeleton ──> M1 hear & respond ──> M2 learning core ──> [dogfood gate] ──> M3 reading
                      │                                                   └─> M4 accounts & sync (parallel with M3)
                      └─> S1 polyphonic spike (parallel, de-risks M5)
M3 + M4 ──> M5 hands ──> M6 progress ──> M7 by ear & import
M3 ──> MP pieces (hands separate; harmonic ear pulled forward from M7; runs beside the T3.17 device week)
```

Two changes to the arch build plan:

1. **Pull a polyphonic transcription spike (S1) forward into M1/M2.** M5 is the highest technical risk; knowing Basic Pitch accuracy on your instruments and iPad early may change the HANDS design (for example, leaning on MIDI-only for HANDS until a better model lands). It needs the fixture corpus from T1.8 and nothing else.
2. **Dogfood gate after M2:** at least one week of daily sessions on iPhone before starting M3, feeding fixes into a short M2.x tail. The learning loop is the product; reading on top of a broken loop wastes work.

## 4. Task breakdown: M0-M2

Notation: **Deps** lists tasks that must merge first. **Accept** lists what the PR's tests or demo must show. Tasks marked **[you]** need you on a real device or instrument.

### M0: Skeleton
